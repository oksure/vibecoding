# §8.3 에이전트는 어떻게 도구를 쓰는가 {#sec-tool-calling-and-sandbox .unnumbered} 8.1절은 모델이 다음 토큰을 하나씩 예측해 코드를 써 내려가는 원리를, 8.2절은 그 모델이 학습으로 만들어지는 과정을 다룬다. 두 절이 설명하는 모델은 텍스트를 출력한다. 그런데 3.2절과 3.5절에서 본 코딩 에이전트는 파일을 고치고, 테스트를 실행하고, 실패하면 다시 고친다. 텍스트를 내놓는 일과 프로그램을 실행하는 일 사이에는 간격이 있다. 이 절은 그 간격이 어떻게 메워지는지를 설명한다. 간격을 메우는 것은 모델 바깥에 있다. 모델은 아무것도 실행하지 않는다. 모델은 어떤 기능을 어떤 입력으로 실행해 달라는 요청을 정해진 형식의 텍스트로 출력하고, 그 텍스트를 읽어 실제로 실행하는 일은 모델 바깥의 프로그램이 맡는다. 이 바깥 프로그램을 하네스(harness)라고 하며, 하네스의 구성 전체는 7.1절에서 다룬다. 이 절은 그 가운데 도구를 호출하고 실행하는 부분을 본다. 이 절의 질문은 두 가지다. 1) 도구 호출은 어떤 구조로 이루어지고, 코딩 에이전트는 무엇을 도구로 쓰는가. 2) 그 실행을 왜, 무엇으로 통제하는가. 도구를 고르고 연결하는 실무는 7.3절에서, 숨은 지시를 이용한 공격과 방어는 9.3절에서, 호출 기록으로 에이전트의 행동을 추적하는 방법은 10.3절에서, 도구 프로토콜 표준화의 영향은 17.4절에서 다룬다. 제품 문서에서 가져온 설명은 2026년 11월 18일에 확인한 내용이다. 인용한 제품 문서에는 문서 자체의 버전이 적혀 있지 않아 확인 날짜만 적고, 판이 있는 자료(MCP 명세, Transformers 문서, 공개 저장소)는 판이나 커밋을 함께 적는다. 제품의 기능과 기본값은 이후 달라질 수 있다. ## 도구 호출의 구조 이 절에서 도구(tool)는 모델이 실행을 요청할 수 있도록 하네스가 이름, 설명, 입력 형식을 붙여 내놓은 기능을 뜻한다. 파일 읽기, 셸 명령(터미널에 입력하는 명령) 실행, 웹 검색이 각각 하나의 도구가 될 수 있다. 모델이 도구의 실행을 요청하는 출력을 도구 호출(tool call)이라고 한다. Anthropic은 이 기능을 tool use, OpenAI는 function calling 또는 tool calling이라고 부르며, Anthropic의 문서는 tool use가 function calling이라고도 불린다고 적는다([Anthropic, Tool use with Claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) (확인: 2026-11-18); [OpenAI, Function calling](https://developers.openai.com/api/docs/guides/function-calling) (확인: 2026-11-18)). 두 문서가 설명하는 흐름도 같다. 이 절은 그 흐름을 네 단계로 정리한다([Anthropic, How tool use works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works) (확인: 2026-11-18)). 1. 하네스가 모델에 요청을 보낼 때, 사용자의 지시와 함께 쓸 수 있는 도구의 목록을 넣는다. 목록의 각 항목이 도구 정의(tool definition)다. 2. 모델은 도구가 필요하다고 판단하면 사용자에게 줄 답 대신 도구 호출을 출력한다. 호출에는 도구의 이름과 입력값이 들어 있다. 3. 하네스가 호출을 해석해 해당 기능을 실제로 실행한다. 4. 하네스가 실행 결과를 대화 기록에 덧붙여 모델에 다시 보낸다. 이 결과를 도구 결과(tool result)라고 한다. 모델은 결과를 보고 다음 호출을 출력하거나, 더 부를 도구가 없으면 사용자에게 줄 답을 출력한다. 2단계부터 4단계까지가 되풀이되는 이 구조를 에이전트 루프(agentic loop)라고 한다. 3.2절이 인용한 Simon Willison의 정의, 곧 에이전트는 목표를 이루기 위해 도구를 반복해서 실행하는 모델이라는 정의가 가리키는 것이 이 루프다. 형식을 예시로 보면 다음과 같다. Anthropic 문서의 형식을 따라 이 절에서 구성한 예시이며, 실제 요청과 응답에는 항목이 더 있다. 형식은 JSON(JavaScript Object Notation, 이름과 값의 쌍으로 데이터를 적는 텍스트 형식)이다. 먼저 하네스가 모델에 건네는 도구 정의다. ```json { "name": "run_command", "description": "작업 폴더에서 셸 명령을 실행하고 출력을 돌려준다.", "input_schema": { "type": "object", "properties": { "command": { "type": "string", "description": "실행할 명령" } }, "required": ["command"] } } ``` 도구 정의는 이름, 설명, 입력 형식으로 이루어진다. 입력 형식은 JSON Schema라는 표기법으로 적으며, 위 정의는 `command`라는 문자열 하나를 반드시 받는다는 뜻이다. 설명은 사람의 말로 쓴 문장이고, 모델은 사용자의 요청과 이 설명을 보고 도구를 부를지 정한다. 테스트를 실행해야 한다고 판단한 모델은 다음과 같은 텍스트를 출력한다. ```json { "type": "tool_use", "id": "toolu_01", "name": "run_command", "input": { "command": "pytest" } } ``` `pytest`는 Python 코드의 테스트를 실행하는 명령이다. 이 출력은 실행해 달라는 요청이고, 이 시점까지 실행된 것은 없다. 하네스가 명령을 실행한 뒤 그 출력을 다음과 같이 돌려준다. ```json { "type": "tool_result", "tool_use_id": "toolu_01", "content": "1 failed in 0.01s" } ``` 모델 쪽에서 보면 이 과정은 8.1절에서 본 다음 토큰 예측과 다르지 않다. 도구 정의는 별도의 통로로 전달되지 않고 프롬프트의 일부가 된다. Anthropic의 문서는 API가 도구 정의와 설정을 넣어 특별한 시스템 프롬프트를 구성한다고 설명하고 그 틀을 공개한다([Anthropic, Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools) (확인: 2026-11-18)). 가중치가 공개된 모델에서는 호출이 텍스트라는 점을 직접 볼 수 있다. Hugging Face Transformers 문서의 예시에서 Hermes-2-Pro-Llama-3-8B 모델은 ``이라는 표지 사이에 도구 이름과 입력값을 담은 JSON을 그대로 생성하고, 이 문자열을 해석해 도구를 실행하는 일은 개발자의 코드가 한다([Hugging Face, Tool use](https://huggingface.co/docs/transformers/v5.17.0/chat_extras) (Transformers 문서 v5.17.0; 확인: 2026-11-18)). Anthropic이 공개한 틀에도 모델의 출력을 정규 표현식으로 해석한다는 문구가 있다. 앞의 예시에 나온 `tool_use` 블록은 모델이 생성한 텍스트를 API가 해석해 정리한 결과인 셈이다. 생성된 텍스트가 형식을 지킨다는 보장은 두 곳에서 나온다. 하나는 학습이고, 뒤에서 다룬다. 다른 하나는 생성 단계의 제약이다. OpenAI는 JSON Schema를 문맥 자유 문법(context-free grammar)으로 바꾸어 두고, 토큰을 하나 생성할 때마다 그 문법에서 올 수 없는 토큰의 확률을 0으로 낮추는 방식을 설명했다. 이 방식을 constrained decoding이라고 한다. 같은 글에 따르면 복잡한 스키마를 따르는지 보는 자체 평가에서 gpt-4o-2024-08-06 모델은 학습만으로 93%였고, 이 제약을 더해 100%가 되었다([OpenAI, Introducing Structured Outputs in the API](https://openai.com/index/introducing-structured-outputs-in-the-api/) (게시: 2024-08-06)). Anthropic도 도구 정의에 `strict` 옵션을 켜면 같은 원리의 제약으로 입력값이 스키마를 따르도록 보장한다고 적는다([Anthropic, Strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use) (확인: 2026-11-18)). 이 보장은 형식에 한정된다. OpenAI의 글은 값 자체는 여전히 틀릴 수 있다고 밝힌다. 앞의 예시로 말하면 `command`가 문자열이라는 것은 보장되지만, 그 문자열이 실행해도 되는 명령인지는 보장되지 않는다. 이 구조에서 세 가지가 따라 나온다. 첫째, 실행을 결정하는 자리는 하네스에 있다. 모델은 도구가 어떻게 구현되어 있는지 받지 못하고, 도구 정의와 돌아온 결과만 본다([Anthropic, How tool use works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works) (확인: 2026-11-18)). 모델이 출력한 호출을 그대로 실행할지, 사람에게 먼저 물을지, 거부할지는 하네스가 정한다. 뒤에서 볼 권한 규칙, 승인, 샌드박스는 모두 이 자리에 놓이는 장치다. 둘째, 에이전트가 한 일은 호출과 결과의 기록으로 남는다. 호출과 결과가 모두 텍스트로 하네스를 거치기 때문이다. 예를 들어 Claude Code는 메시지, 도구 사용, 결과를 하나하나 사용자 컴퓨터의 파일에 기록한다고 문서에 적고 있다([Anthropic, How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works) (확인: 2026-11-18)). 에이전트가 무엇을 읽었고 무엇을 바꿨는지를 나중에 되짚을 수 있으므로, 이 기록은 제3부의 질문인 ‘어떻게 믿을까’에 답하는 재료가 된다. 기록을 읽고 활용하는 방법은 10.3절에서 다룬다. 셋째, 도구는 컨텍스트 윈도(context window, 모델이 한 번에 참조할 수 있는 토큰의 한도)를 차지한다. 도구 정의는 요청마다 입력에 들어가고, 호출과 결과도 대화 기록에 쌓인다. Anthropic의 문서는 도구의 이름, 설명, 입력 형식과 호출 및 결과가 모두 토큰으로 계산된다고 밝히고, OpenAI의 문서도 함수 정의가 모델의 컨텍스트 한도에 포함되며 입력 토큰으로 과금된다고 적는다([Anthropic, Tool use with Claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) (확인: 2026-11-18); [OpenAI, Function calling](https://developers.openai.com/api/docs/guides/function-calling) (확인: 2026-11-18)). 연결한 도구가 많고 결과가 길수록 비용이 늘고, 모델이 작업에 쓸 수 있는 공간은 줄어든다. 비용은 루프의 구조 때문에 더 빨리 는다. 하네스는 호출이 한 번 끝날 때마다 그때까지의 메시지 전체에 새 결과를 덧붙여 다시 요청을 보내므로, 앞부분의 내용은 호출 횟수만큼 되풀이해 입력된다. 호출마다 덧붙는 분량이 비슷하다고 가정하면 누적 입력 토큰은 호출 횟수의 제곱에 비례해 늘어난다. 이 계산은 이 절의 추정이다. 이 부담을 줄이는 장치가 프롬프트 캐싱(prompt caching)이다. Anthropic의 문서에 따르면 캐시는 도구 정의, 시스템 프롬프트, 메시지 순서로 이어지는 요청의 앞부분에 적용되고, 캐시에서 읽은 토큰은 기본 입력 가격의 0.1배로 계산된다(모델에 따라 배수가 다르다). 도구 정의가 맨 앞에 놓이므로 도구 정의를 바꾸면 캐시 전체가 무효가 된다([Anthropic, Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) (확인: 2026-11-18)). 컨텍스트 윈도를 관리하는 방법은 5.2절과 6.3절에서 다룬다. ## 도구 호출 능력은 어떻게 만들어졌나 모델이 위와 같은 형식의 호출을 출력하는 것은 그렇게 하도록 만들어졌기 때문이다. 제품이 출시된 순서는 3.2절에서 다루었으므로, 여기서는 호출 형식이 어디에 담겨 있었는지를 기준으로 본다. 처음에는 형식이 프롬프트에 있었다. Yao 등의 ReAct는 모델에게 예시 몇 개를 보여 주어 추론(reasoning)과 행동(acting)을 번갈아 텍스트로 적게 했다. 모델이 적은 행동을 바깥의 프로그램이 실행하고, 그 결과를 다음 입력에 붙여 주는 방식이다. 논문은 위키백과를 검색하는 간단한 API(application programming interface, 프로그램이 다른 프로그램의 기능을 불러 쓰는 통로)를 행동으로 쓰게 해 질의응답과 사실 검증 과제를 풀게 했다([Yao 외, ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/abs/2210.03629) (ICLR 2023 본 학회; 프리프린트 공개: 2022-10-06)). 구조는 앞에서 본 루프와 같지만, 모델이 형식을 지키는지는 프롬프트에 넣은 예시에 달려 있었다. 다음에는 형식이 학습으로 옮겨 갔다. Schick 등의 Toolformer는 어떤 API를 언제, 어떤 입력값으로 부르고 그 결과를 어떻게 이어 쓸지를 모델이 학습하게 했다. 이 논문에서 API 호출은 본문 사이에 끼워 넣는 텍스트로 표현된다. 저자들은 기존 언어 모델에게 예시 몇 개를 보여 주어 일반 텍스트에 호출 후보를 달게 하고, 그 호출을 실제로 실행한 뒤, 호출과 결과를 넣었을 때 뒤따르는 토큰의 예측 손실이 기준 이상 줄어드는 경우만 남겨 학습 데이터로 삼았다. 사람이 정답을 달지 않아도 모델의 예측에 도움이 되는 호출만 걸러지는 방식이다. 도구로는 계산기, 질의응답 시스템, 검색 엔진, 번역 시스템, 달력을 썼다([Schick 외, Toolformer: Language Models Can Teach Themselves to Use Tools](https://proceedings.neurips.cc/paper/2023/hash/d842425e4bf79ba039352da0f658a906-Abstract.html) (NeurIPS 2023 본 학회; 프리프린트 공개: 2023-02-09)). 2023년 6월 OpenAI는 개발자가 함수를 JSON Schema로 설명하면 모델이 그 함수에 넣을 입력값을 JSON으로 출력하는 기능을 API에 넣었다. OpenAI는 함수를 불러야 할 때를 알아차리고 형식에 맞는 JSON을 내놓도록 모델을 미세조정(fine-tuning)했다고 밝혔다([OpenAI, Function calling and other API updates](https://openai.com/index/function-calling-and-other-api-updates) (게시: 2023-06-13)). 지금의 문서에도 같은 설명이 있다. Anthropic은 셸 명령 실행, 파일 편집, 데스크톱과 브라우저 조작처럼 자사가 입력 형식을 정해 둔 도구는 모델이 그 형식을 학습했기 때문에 더 안정적으로 호출한다고 설명한다([Anthropic, How tool use works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works) (확인: 2026-11-18)). 모델이 이런 능력을 얻는 학습 과정은 8.2절에서 다룬다. 도구를 모델에 연결하는 방식도 규약으로 정리되었다. Anthropic은 데이터 원천마다 연결을 따로 구현해야 하는 문제를 이유로 들며 2024년 11월에 MCP(Model Context Protocol)를 공개했다([Anthropic, Introducing the Model Context Protocol](https://www.anthropic.com/news/model-context-protocol) (게시: 2024-11-25)). MCP는 도구를 제공하는 프로그램을 서버, 그것을 가져다 쓰는 AI 애플리케이션을 클라이언트라고 부르고, 클라이언트가 서버에 도구 목록을 요청하는 메시지와 도구를 호출하는 메시지의 형식을 정한다. 서버가 돌려주는 도구 정의에도 이름, 설명, 입력 형식이 들어 있다([Model Context Protocol, Specification: Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) (명세 판: 2025-11-25; 확인: 2026-11-18)). 2025년 12월 Anthropic은 MCP를 Linux Foundation이 새로 만든 Agentic AI Foundation에 기증했고, Linux Foundation의 보도자료는 공개된 MCP 서버가 1만 개를 넘는다고 적었다([Linux Foundation, Linux Foundation Announces the Formation of the Agentic AI Foundation (AAIF)](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation) (게시: 2025-12-09)). 서버 수는 발표 주체가 밝힌 수치다. MCP 서버를 연결하고 설계하는 방법은 7.3절에서, 표준화가 생태계에 미칠 영향은 17.4절에서 다룬다. ## 코딩 에이전트가 쓰는 도구 코딩 에이전트의 하네스는 개발자가 컴퓨터에서 하던 일을 도구로 내놓는다. Claude Code의 문서는 기본 도구를 파일 작업, 검색, 실행, 웹, 코드 인텔리전스(편집 뒤의 타입 오류 확인, 정의로 이동 등)의 다섯 범주로 나누고, 그 밖의 기능은 MCP 같은 확장으로 더한다고 설명한다([Anthropic, How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works) (확인: 2026-11-18)). 제품마다 도구의 이름과 묶는 방식은 다르다. 이 절은 도구가 닿는 대상에 따라 파일, 명령어, 웹과 브라우저, 외부 서비스의 API로 나누어 본다. 이 구분은 뒤에서 통제 장치를 설명하기 위해 이 절이 세운 것이다. | 대상 | 도구가 하는 일 | 호출이 남기는 영향 | | ---- | ---------- | -------------- | | 파일 | 파일 읽기, 내용 검색, 수정, 새 파일 만들기 | 읽기와 검색은 아무것도 바꾸지 않는다. 수정은 작업 폴더의 파일을 바꾼다. | | 명령어 | 테스트, 빌드, 버전 관리, 패키지 설치 같은 셸 명령 실행 | 사용자가 터미널에서 할 수 있는 일을 대부분 할 수 있다. 파일 삭제와 외부 전송도 여기에 든다. | | 웹과 브라우저 | 웹 검색, 문서 가져오기, 브라우저 화면 조작 | 다른 사람이 쓴 글이 모델의 입력으로 들어온다. 화면 조작은 로그인된 서비스의 상태를 바꿀 수 있다. | | 외부 서비스의 API | 이슈 관리 도구, 데이터베이스, 배포 시스템 등의 기능 호출 | 원격 시스템의 상태를 바꾼다. | 표의 오른쪽 열이 대상마다 다르다는 점이 뒤에서 중요해진다. 되돌릴 수 있는지도 다르다. Claude Code의 같은 문서에 따르면 파일 수정은 수정 전 내용을 보관해 두는 체크포인트(checkpoint)로 되돌릴 수 있지만, 데이터베이스, API, 배포처럼 원격 시스템에 한 행동은 체크포인트로 되돌릴 수 없다. 명령어 도구는 넷 가운데 범위가 가장 넓다. 테스트 실행과 파일 삭제가 같은 도구 하나로 이루어지므로, 도구의 이름만 보고는 허용 여부를 정하기 어렵다. 브라우저와 데스크톱 화면을 조작하는 일도 같은 형식의 도구로 제공되며, 화면을 조작하는 에이전트는 16.4절에서 다룬다. ## 요청 하나가 여러 번의 호출로 풀리는 과정 아래 표는 한 번 실행해 얻은 기록이다. 조건을 먼저 적는다. 대상은 월별 매출의 합계와 평균을 계산하는 연습용 Python 프로젝트다. 함수 8개와 테스트 18건으로 이루어져 있다. 버그는 스크립트가 넣었다. 스크립트는 연산자나 숫자 하나를 바꾸는 변경 53가지 가운데 하나를 무작위로 골라 적용하고, 테스트가 실패하는 것만 확인한 뒤 바꾼 위치를 별도 파일에 감추었다. 과제를 맡은 것은 이 프로젝트를 처음 보는 에이전트다. 준비를 맡은 세션이 서브에이전트(subagent, 따로 띄워 일을 맡기는 별도의 에이전트)를 새로 시작하고, “(폴더 경로) 폴더의 프로젝트에서 실패하는 테스트를 고쳐 줘”라는 한 문장만 전달했다. 괄호 자리에는 과제 폴더의 실제 경로를 적었다. 프로젝트의 내용과 버그의 위치는 알려 주지 않았다. 서브에이전트에게 일을 나누어 맡기는 방법은 16.1절에서 다룬다. 실행 날짜는 2026년 11월 18일이다. 실행 환경은 Anthropic의 Claude 앱이 제공하는 클라우드 작업 환경이며, 이 환경은 하네스의 버전을 표시하지 않는다. 모델은 서브에이전트가 자신의 시스템 프롬프트에서 읽어 보고한 바로는 Claude Fable 5.2(모델 ID `claude-fable-5-2`)다. Python 3.13.18과 pytest 9.1.1을 썼다. 표의 `Bash`, `Read`, `Edit`는 이 환경의 실제 도구 이름이다. 앞의 형식 예시에서 `run_command`라고 부른 도구가 여기서는 `Bash`다. 기록을 얻은 방법도 밝혀 둔다. 이 환경은 서브에이전트의 세션 기록 파일을 남기지 않는다. 그래서 작업이 끝난 뒤 같은 서브에이전트에게 자신이 한 호출과 받은 결과를 대화 기록에서 그대로 옮겨 적게 했고, 표는 그 내용을 줄여 실었다. 에이전트가 옮겨 적은 것이므로 두 가지를 따로 대조했다. 하네스가 보고한 도구 호출 횟수는 6회로 표와 같았다. 테스트 명령의 출력은 같은 버그를 넣은 복사본에서 다시 실행한 결과와 같았다. 실행마다 달라지는 함수의 메모리 주소와 실행 시간은 무관하다. 6번의 테스트 재실행은 5번의 수정이 끝나야 의미가 있는데, 이 실행에서는 하네스가 두 호출을 적힌 순서대로 실행해 문제가 없었다. 작업을 마쳤다는 보고와 6번 결과는 종류가 다른 정보다. 보고는 모델이 쓴 문장이고, 6번 결과는 하네스가 명령을 실행해 얻은 출력이다. 이 기록에는 그 차이가 드러나는 대목이 있다. 서브에이전트의 보고에는 이 폴더가 git 저장소가 아니어서 커밋하지 않았다는 문장이 있었다. 그런데 기록에는 git 명령을 실행한 호출이 없다. 이 판단의 근거는 1번의 파일 목록에 `.git` 폴더가 보이지 않았다는 것뿐이었고, 기록을 옮겨 적으면서 에이전트 스스로도 그렇게 밝혔다. 따로 확인해 보니 결론은 맞았다. 그래도 보고에 적힌 문장이 모두 실행으로 확인된 것은 아니다. 작업이 끝났는지를 판단할 근거는 호출의 결과 쪽에 있다. 3.5절이 끝났다는 보고와 끝났다는 증거를 구분하라고 한 것도 이 차이를 가리킨다. 하네스가 보고한 사용량은 도구 호출 6회, 실행 시간 약 13.6초, 토큰 68,999개였다. 고친 것은 한 줄이다. 이 환경은 토큰의 내역을 보여 주지 않으므로 무엇이 얼마를 차지했는지는 알 수 없다. 다만 요청마다 도구 정의와 그때까지의 기록이 다시 입력된다는 앞의 설명과 어긋나지 않는 크기다. ## 도구의 형태가 결과를 바꾼다 모델이 보는 것은 도구 정의와 도구 결과의 텍스트다. 그러므로 같은 모델이라도 그 텍스트를 어떻게 만들어 주느냐에 따라 결과가 달라질 수 있다. Yang 등은 이 차이를 직접 비교했다. 저자들은 에이전트가 컴퓨터를 다루는 데 쓰는 인터페이스를 에이전트-컴퓨터 인터페이스(agent-computer interface, ACI)라고 부르고, 파일 보기, 검색, 편집 명령을 모델에 맞게 새로 설계했다. 실제 오픈소스 저장소의 이슈를 해결하게 하는 벤치마크 SWE-bench의 300문제 부분집합(SWE-bench Lite)에서, 같은 모델 GPT-4 Turbo에 셸만 준 에이전트는 11.00%를 해결했고 새 인터페이스를 준 에이전트는 18.00%를 해결했다([Yang 외, SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering](https://arxiv.org/abs/2405.15793) (NeurIPS 2024 본 학회; 표 1)). 인터페이스의 요소를 하나씩 바꾼 비교에서는 파일을 100줄씩 나누어 보여 줄 때 18.0%, 파일 전체를 한 번에 보여 줄 때 12.7%였다. 문법 오류가 생기는 수정을 받아들이지 않는 검사를 편집 명령에 넣었을 때는 18.0%, 뺐을 때는 15.0%였다(같은 논문, 표 3). 이 수치는 2024년의 모델과 특정 벤치마크에서 얻은 것이므로 지금의 성능을 말해 주지 않는다. 이 결과에서 가져올 것은 방향이다. 사람이 쓰기 편한 인터페이스가 모델에게도 맞는다고 가정할 수 없고, 더 많이 보여 주는 쪽이 항상 낫지도 않다. SWE-bench 점수의 변화는 3.2절에서, 벤치마크 점수를 읽는 법은 10.4절에서 다룬다. 호출을 어떤 형식으로 적게 하느냐도 비교되었다. Wang 등의 CodeAct는 모델이 JSON이나 정해진 텍스트 형식 대신 실행 가능한 Python 코드로 행동을 적게 했다. 코드로 적으면 한 번의 출력 안에서 여러 도구를 이어 부를 수 있다. 저자들은 17개 모델을 비교해 이 방식의 성공률이 최대 20% 높았다고 보고했다([Wang 외, Executable Code Actions Elicit Better LLM Agents](https://arxiv.org/abs/2402.01030) (ICML 2024 본 학회)). API-Bank와 저자들이 새로 만든 벤치마크에서 얻은 결과다. Anthropic의 엔지니어링 블로그는 같은 생각을 MCP에 적용한 사례를 소개했다. 도구를 하나씩 직접 호출하면 모든 도구의 정의와 중간 결과가 컨텍스트 윈도를 거치지만, 모델이 도구를 부르는 코드를 쓰고 그 코드를 별도의 실행 환경에서 돌리면 필요한 정의만 읽고 중간 결과는 그 환경 안에서 처리할 수 있다는 것이다. 글은 한 예시에서 토큰 사용량이 15만에서 2천으로, 98.7% 줄었다고 적었다([Anthropic, Code execution with MCP: Building more efficient agents](https://www.anthropic.com/engineering/code-execution-with-mcp) (게시: 2025-11-04)). 기업이 자사 블로그에 소개한 사례 하나이고 측정 조건이 자세히 공개되지 않았으므로, 일반적인 절감률로 읽을 수 없다. 같은 글은 이 방식의 비용도 밝힌다. 모델이 쓴 코드를 실행하려면 샌드박스와 자원 제한, 모니터링을 갖춘 실행 환경이 따로 필요하다. 도구를 만드는 쪽의 지침도 같은 방향을 가리킨다. Anthropic의 다른 글은 도구를 결정론적 시스템과 비결정론적 에이전트 사이의 계약("a contract between deterministic systems and non-deterministic agents")이라고 표현한다. 글은 도구를 많이 늘어놓기보다 목적이 분명한 소수의 도구를 두고, 결과를 간결하게 돌려주고, 오류 메시지에 무엇을 고쳐야 하는지를 담으라고 권한다([Anthropic, Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (게시: 2025-09-11)). 이 글도 기업 기술 블로그이며 자사의 경험을 정리한 것이다. 호출이 실패했을 때 그 사실을 결과로 돌려주는 것도 형태의 일부다. MCP 명세는 입력값 오류 같은 실행 오류를 도구 결과에 담아 모델에 전달하라고 권한다. 모델이 그 내용을 보고 입력값을 고쳐 다시 시도할 수 있기 때문이다([Model Context Protocol, Specification: Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) (명세 판: 2025-11-25; 확인: 2026-11-18)). 어떤 도구를 연결하고 설명을 어떻게 쓸지는 7.3절에서 다룬다. ## 틀린 출력이 실행으로 이어질 때 도구가 없는 모델의 오류는 화면에 나타난 문장으로 남고, 그 문장을 쓸지는 사람이 정한다. 도구를 쓰는 에이전트에서는 같은 오류가 호출의 형태로 출력되고, 하네스가 막지 않으면 실행된다. 실행으로 이어지는 경로는 둘로 나누어 볼 수 있다. 하나는 잘못된 호출이다. 없는 파일을 열거나, 입력값을 틀리게 넣거나, 맞지 않는 도구를 고르는 경우다. Patil 등의 BFCL(Berkeley Function Calling Leaderboard)은 이런 호출 정확도를 따로 평가하는 벤치마크다. 저자들은 최신 모델이 한 번의 호출은 잘 해내지만, 여러 단계에 걸친 작업에 필요한 기억, 상황에 따른 판단, 긴 추론은 아직 과제로 남아 있다고 보고했다([Patil 외, The Berkeley Function Calling Leaderboard (BFCL): From Tool Use to Agentic Evaluation of Large Language Models](https://proceedings.mlr.press/v267/patil25a.html) (ICML 2025 본 학회)). 형식이 틀린 호출은 대개 오류로 돌아오므로 다시 시도하면 된다. 다루기 어려운 것은 형식은 맞고 내용이 틀린 호출이다. 지워서는 안 되는 폴더를 지우는 명령은 오류 없이 실행된다. 다른 하나는 오염된 입력이다. 도구 결과는 모델의 입력이 되므로, 도구가 가져온 웹페이지나 문서에 지시처럼 읽히는 문장이 들어 있으면 모델이 그것을 따를 수 있다. Greshake 등은 이를 간접 프롬프트 인젝션(indirect prompt injection)이라고 부르고, 외부에서 가져온 텍스트가 애플리케이션의 동작을 바꾸고 다른 API를 호출할지와 어떻게 호출할지까지 조종할 수 있음을 실제 서비스와 실험용 애플리케이션에서 보였다([Greshake 외, Not What You've Signed Up For: Compromising Real-World LLM-Integrated Applications with Indirect Prompt Injection](https://arxiv.org/abs/2302.12173) (AISec '23, ACM CCS 워크숍 논문)). 이 문제가 구조적인 이유는 모델의 입력에서 지시와 데이터가 구분되지 않기 때문이다. 시스템 프롬프트, 사용자의 요청, 도구 결과는 하나의 토큰 열로 이어져 모델에 들어가고, 모델은 어떤 문장이 어디에서 왔는지에 따라 그 지시의 무게를 믿을 만하게 가리지 못한다([Simon Willison, The lethal trifecta for AI agents: private data, untrusted content, and external communication](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) (개인 블로그; 게시: 2025-06-16)). OpenAI도 2023년에 function calling을 발표하면서, 도구 출력에 든 신뢰할 수 없는 데이터가 모델에게 의도하지 않은 행동을 시킬 수 있다고 경고하고 실제 영향이 있는 행동 앞에는 사용자 확인 단계를 두라고 권했다([OpenAI, Function calling and other API updates](https://openai.com/index/function-calling-and-other-api-updates) (게시: 2023-06-13)). 지시는 도구 결과뿐 아니라 도구 정의에도 숨을 수 있다. 보안 업체 Invariant Labs는 덧셈 도구의 설명에 숨긴 지시로, 에이전트가 SSH 개인 키(원격 서버에 접속할 때 본인임을 증명하는 비밀 파일)를 읽어 도구의 입력값으로 넘기게 하는 시연을 공개했다([Invariant Labs, MCP Security Notification: Tool Poisoning Attacks](https://invariantlabs.ai/blog/mcp-security-notification) (게시: 2025-04-01)). 이 자료는 동료 심사를 거치지 않은 업체 블로그다. 공격의 유형과 방어는 9.3절에서 다룬다. 두 경로에서 나온 호출이 얼마나 큰 문제가 되는지는 그 행동을 되돌릴 수 있는지에 달려 있다. 앞에서 본 것처럼 파일 수정은 되돌릴 수단이 있지만, 원격 저장소에 올린 변경, 보낸 메시지, 배포, 데이터베이스 수정은 하네스가 되돌리지 못한다. ## 실행을 통제하는 세 장치: 권한 규칙, 승인, 샌드박스 두 경로 모두 모델이 출력한 호출에서 시작하고, 호출은 하네스를 거쳐야 실행된다. 그래서 통제는 하네스에 둔다. 모델이 잘못된 호출을 하지 않도록 학습시키고 지시하는 일도 필요하지만, 모델의 출력은 확률적이고 입력에 따라 달라지므로 그것만으로 실행을 막을 수는 없다. 이 절은 Claude Code와 OpenAI Codex의 공식 문서를 바탕으로 세 가지 장치를 설명한다. 권한 규칙의 예는 Claude Code의 것이고, 승인과 샌드박스는 두 제품에 공통된 구조를 중심으로 적는다. 권한 규칙은 어떤 호출을 허용하고, 어떤 호출을 사람에게 묻고, 어떤 호출을 거부할지를 미리 적어 둔 목록이다. Claude Code에서는 도구 이름과 대상의 패턴으로 규칙을 쓴다. 예를 들어 `Bash(npm run *)`는 `npm run`으로 시작하는 셸 명령에, `Read(~/secrets/**)`는 특정 폴더 아래의 파일 읽기에 적용되는 규칙이다([Anthropic, Tools reference](https://code.claude.com/docs/en/tools-reference) (확인: 2026-11-18)). 거부 규칙은 어떤 권한 모드에서도 적용된다([Anthropic, Choose a permission mode](https://code.claude.com/docs/en/permission-modes) (확인: 2026-11-18)). 규칙의 한계는 모델이 쓴 명령의 글자에 적용된다는 데 있다. Claude Code는 `&&` 같은 셸 연산자로 이어 붙인 명령을 나누어 각각을 규칙과 맞춰 본다. 그래도 같은 프로그램을 다른 형태로 부르면 규칙에 걸리지 않으므로, 문서는 Bash 규칙이 프로그램을 둘러싼 보안 경계는 아니라고 적는다. 예를 들어 `Bash(curl *)`를 거부해도 `sh -c 'curl ...'` 형태의 호출은 이 규칙에 걸리지 않는다. 문서는 명령의 글자에 의존하지 않는 제한이 필요하면 샌드박스를 쓰라고 안내한다([Anthropic, Configure permissions](https://code.claude.com/docs/en/permissions) (확인: 2026-11-18)). 승인은 호출을 실행하기 전에 사람에게 보여 주고 허락을 받는 절차다. 얼마나 자주 물을지는 권한 모드(permission mode)로 정한다. Claude Code의 문서에 따르면 수동(Manual) 모드에서는 읽기만 묻지 않고 실행하고, 파일 수정과 셸 명령은 실행 전에 묻는다. 자동(Auto) 모드에서는 별도의 분류기 모델이 호출을 검토해 위험하다고 판단한 것을 막는데, 문서는 이 모드가 승인 요청을 줄일 뿐 안전을 보장하지는 않는다고 적는다. 모든 확인을 건너뛰는 모드도 있으며, 문서는 이 모드를 인터넷 접근이 없는 컨테이너나 가상 머신 같은 격리된 환경에서만 쓰라고 경고한다([Anthropic, Choose a permission mode](https://code.claude.com/docs/en/permission-modes) (확인: 2026-11-18)). 승인에는 한계가 있다. 요청이 잦으면 사람은 내용을 읽지 않고 허용하게 된다. Anthropic은 자사 원격 측정에서 사용자가 승인 요청의 약 93%를 허용했다고 밝히고, 승인 요청을 많이 볼수록 요청 하나하나에 기울이는 주의가 줄어든다고 설명했다([Anthropic, How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude) (게시: 2026-05-25)). 이 현상을 승인 피로(approval fatigue)라고 한다. 승인이 통제로 기능하려면 사람이 요청을 읽고 판단해야 하는데, 묻는 횟수가 늘수록 그 전제가 약해진다. 승인 지점을 어디에 둘지는 6.4절에서 다룬다. 샌드박스(sandbox)는 프로그램이 접근할 수 있는 범위를 운영체제 수준에서 제한하는 장치다. 권한 규칙과 승인은 명령이 실행되기 전에 실행 여부를 정하고, 샌드박스는 실행 중인 명령이 어디까지 닿을 수 있는지를 정한다. 제한하는 대상은 파일 시스템과 네트워크다. Claude Code의 샌드박스는 기본으로는 꺼져 있고, 켜면 셸 명령과 그 명령이 띄운 프로세스가 작업 폴더와 임시 폴더에만 쓸 수 있으며 네트워크 연결은 허용한 도메인으로만 나간다. 이 제한은 macOS의 Seatbelt, Linux의 bubblewrap 같은 운영체제 기능으로 강제된다([Anthropic, Configure the sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing) (확인: 2026-11-18)). OpenAI Codex의 문서는 같은 구조를 두 층으로 설명한다. 샌드박스는 에이전트가 기술적으로 할 수 있는 일을 정하고, 승인 정책은 언제 사람에게 물어야 하는지를 정한다. 로컬에서 실행할 때의 기본값은 네트워크 접근을 끄고 쓰기를 작업 폴더로 제한하는 것이다([OpenAI, Agent approvals & security](https://learn.chatgpt.com/codex/agent-approvals-security) (확인: 2026-11-18)). 구현을 보면 이 제한이 모델의 판단과 무관하게 지켜지는 이유가 드러난다. Claude Code의 샌드박스가 쓰는 공개 런타임(sandbox-runtime)의 문서에 따르면, Linux에서는 bubblewrap으로 프로세스를 감싸면서 그 프로세스의 network namespace(프로세스에 보이는 네트워크 환경)를 없앤다. 샌드박스 안의 프로세스에는 바깥으로 직접 나가는 길이 없고, 샌드박스 안에 연결해 둔 Unix domain socket(같은 컴퓨터의 프로세스끼리 통신하는 통로) 너머의 프록시(proxy, 통신을 대신 전달하는 중계 프로그램)만 남는다. 호스트에서 실행되는 이 프록시가 허용 목록을 검사한다. macOS에서는 Seatbelt 프로필이 특정 로컬 포트와의 통신만 허용하고 프록시가 그 포트에서 기다린다. 이 제한은 감싼 프로세스가 띄운 모든 하위 프로세스에 적용된다([Anthropic, sandbox-runtime README](https://github.com/anthropics/sandbox-runtime) (공개 저장소; 확인: 2026-11-18; 커밋 0bbebed, 2026-11-12)). 모델이 어떤 명령을 쓰든, 그 명령이 어떤 프로그램을 거쳐 실행되든 결과는 같다. 파일 시스템과 네트워크를 함께 막아야 하는 이유는 한쪽만 막으면 다른 쪽이 우회로가 되기 때문이다. Anthropic의 설명에 따르면 네트워크 제한이 없으면 조종당한 에이전트가 SSH 키 같은 민감한 파일을 바깥으로 보낼 수 있고, 파일 시스템 제한이 없으면 샌드박스를 벗어나 네트워크 접근을 얻을 수 있다([Anthropic, Beyond permission prompts: making Claude Code more secure and autonomous](https://www.anthropic.com/engineering/claude-code-sandboxing) (게시: 2025-10-20)). 샌드박스는 승인 피로를 줄이는 수단이기도 하다. 경계 안에서 일어나는 일은 묻지 않고 실행해도 피해가 경계 안에 머물기 때문이다. 같은 글은 내부 사용에서 샌드박스가 승인 요청을 84% 줄였다고 밝혔다. 자사 내부 사용에서 얻은 수치이며 외부에서 검증된 것은 아니다. | 장치 | 정하는 것 | 작동하는 때 | 한계 | | ---- | -------- | -------- | ---------- | | 권한 규칙 | 어떤 도구와 대상을 허용, 확인, 거부할지 | 호출을 실행하기 전 | 명령의 글자를 보고 판단하므로 같은 일을 다른 형태로 하는 호출을 놓칠 수 있다 | | 승인 | 이 호출을 지금 실행할지 | 호출을 실행하기 전, 사람이나 분류기가 판단 | 요청이 잦으면 읽지 않고 허용하게 된다 | | 샌드박스 | 실행된 명령이 닿을 수 있는 파일과 네트워크의 범위 | 명령이 실행되는 동안, 운영체제가 강제 | 샌드박스가 감싸지 않는 도구에는 적용되지 않는다 | 세 장치는 서로를 대신하지 못한다. Claude Code의 샌드박스는 셸 명령에만 적용된다. 파일을 읽고 고치는 도구와 웹 도구는 샌드박스 밖에서 권한 규칙을 따르고, 로컬에서 실행되는 MCP 서버도 샌드박스 밖에 있다. 켜 둔 상태에서도 읽기는 기본적으로 컴퓨터의 대부분에 열려 있어서, 자격 증명 파일을 읽는 것 자체는 막지 않는다([Anthropic, Configure the sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing) (확인: 2026-11-18)). 네트워크 허용 목록에도 빈틈이 있다. Anthropic은 허용된 도메인을 통해 작업 폴더의 파일이 공격자의 계정으로 올라간 사례를 소개하고, 허용 목록은 목적지를 거르는 장치라기보다 그 도메인에서 쓸 수 있는 기능 전체를 열어 주는 것으로 보아야 한다고 정리했다([Anthropic, How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude) (게시: 2026-05-25)). MCP 명세도 신뢰와 보안을 위해 도구 호출을 거부할 수 있는 사람이 항상 과정 안에 있어야 한다고 권고하고, 클라이언트가 도구에 넘길 입력값을 사용자에게 보여 주고 도구 사용을 기록으로 남기라고 권한다([Model Context Protocol, Specification: Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) (명세 판: 2025-11-25; 확인: 2026-11-18)). 격리의 강도에도 단계가 있다. Claude Code의 문서는 명령 단위의 샌드박스, 하네스 프로세스 전체를 감싸는 샌드박스 런타임, 컨테이너, 가상 머신을 비교하고, 자체 커널(kernel, 운영체제의 핵심부)을 갖는 가상 머신이 가장 강한 분리를 제공한다고 적는다. 같은 문서는 어떤 방식이든 격리는 침해의 영향을 줄일 뿐 위험을 없애지 못한다고 경고한다. 바깥으로 나가는 네트워크 경로가 열려 있으면 에이전트가 읽을 수 있는 데이터는 여전히 새어 나갈 수 있기 때문이다([Anthropic, Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments) (확인: 2026-11-18)). 어느 단계를 고를지는 사용자가 누구인지에 따라 달라진다. 승인은 사용자가 요청의 뜻을 판단할 수 있을 때 통제가 된다. 앞에서 인용한 Anthropic의 글(How we contain Claude across products)은 사용자가 에이전트의 행동을 감독할 수 있는 정도에 맞추어 제품마다 격리 방식을 달리했다고 설명한다. 셸 명령을 읽을 수 있는 개발자가 주로 쓰는 Claude Code에는 승인과 운영체제 샌드박스를 두었고, 셸 명령에 익숙하지 않은 사용자가 많은 Claude Cowork에는 사용자의 승인에 기대지 않는 로컬 가상 머신을 두었다는 것이다. 코드를 읽지 않고 결과만 확인하며 작업하는 사용자에게도 같은 판단이 적용된다. 명령마다 승인을 묻기보다 사용자가 판단하지 않아도 지켜지는 경계를 두는 편이 낫다. 뒤의 두 문장은 이 절의 해석이다. 이 구조에서, 에이전트에게 작업을 맡기기 전에 확인할 것을 세 가지로 정리할 수 있다. 연구로 검증된 절차가 아니고, 위의 자료를 바탕으로 이 절이 제안하는 점검 항목이다. 1. 이 작업에서 에이전트가 할 수 있는 행동 가운데 되돌릴 수 없는 것은 무엇인가. 원격 저장소에 올리기, 배포, 데이터베이스 수정, 메시지 전송이 가능하다면 그 호출은 자동으로 허용하지 않고 승인 대상으로 남긴다. 2. 에이전트가 읽게 될 것 가운데 내가 쓰지 않은 텍스트는 무엇인가. 웹페이지, 외부 문서, 다른 사람이 만든 MCP 서버의 도구 설명이 들어온다면, 그 세션에서는 비밀 정보가 든 파일과 네트워크 접근을 함께 열어 두지 않는다. 3. 묻지 않고 실행되게 한 범위가 운영체제 수준의 경계 안에 있는가. 승인을 생략하려면 샌드박스나 컨테이너처럼 모델의 판단과 무관하게 지켜지는 경계를 먼저 둔다. 두 번째 항목은 앞에서 인용한 Willison의 글이 치명적 삼중 조합(lethal trifecta)이라고 부른 조건을 피하려는 것이다. 비공개 데이터에 대한 접근, 신뢰할 수 없는 콘텐츠에 대한 노출, 외부와 통신하는 능력이 한 에이전트에 모이면 숨은 지시 하나로 데이터가 유출될 수 있다는 것이 그 글의 요지다. ## 적용 조건과 한계 이 절의 설명은 Anthropic과 OpenAI가 공개한 문서와 MCP 명세에 공통으로 나타나는 구조를 일반화한 것이다. 다른 하네스는 도구의 이름, 권한 모드의 종류, 샌드박스가 감싸는 범위가 다를 수 있다. 제품 문서의 내용은 2026년 11월 18일에 확인했고, 기본값과 모드의 이름은 그 뒤에 바뀔 수 있다. 실제로 쓰는 도구의 문서에서 현재의 기본값을 확인해야 한다. 인용한 수치는 성격이 다르다. SWE-agent와 CodeAct의 수치는 동료 심사를 거친 논문에서 왔지만 2024년의 모델과 특정 벤치마크에서 얻은 것이다. 스키마 준수율 100%, 승인 요청 허용 비율 93%, 승인 요청 감소 84%, 토큰 절감 98.7%, MCP 서버 1만 개는 기업과 재단이 스스로 밝힌 수치이며 독립적으로 검증되지 않았다. 이 절은 이 수치들을 그런 현상이 보고되었다는 근거로만 쓰고, 효과의 크기를 일반화하는 데는 쓰지 않는다. 앞의 여섯 단계 기록은 한 번의 실행에서 얻은 것이다. 과제는 작은 연습 프로젝트에 넣은 한 줄짜리 버그였다. 표의 내용은 에이전트가 자신의 기록을 옮겨 적은 것이고 하네스가 남긴 원본 로그가 아니며, 호출 횟수와 테스트 출력만 따로 대조했다. 이 기록은 호출과 결과가 이어지는 방식을 보여 주는 예이며, 에이전트가 버그를 얼마나 잘 고치는지에 대한 근거가 아니다. 더 큰 과제에서 호출이 몇 번 일어나고 얼마나 자주 실패하는지는 이 기록으로 판단할 수 없고, 같은 과제를 다시 실행해도 호출의 순서와 횟수는 달라질 수 있다. 세 장치를 모두 갖추어도 남는 문제가 있다. 형식과 권한은 맞지만 의도와 다른 호출, 예를 들어 허용된 작업 폴더 안에서 엉뚱한 파일을 고치는 호출은 어느 장치에도 걸리지 않는다. 이런 변경은 실행 뒤의 검토와 테스트로 찾아야 한다. 요청하지 않은 수정의 문제는 9.2절에서, 테스트로 결과를 확인하는 방법은 10장에서 다룬다. 기록이 남는다는 것과 사람이 그 기록을 읽는다는 것도 별개다. 호출이 수십 번을 넘어가면 기록 전체를 읽기 어렵다. 무엇을 그대로 남기고 무엇을 요약해 보여 줄지는 10.3절에서 다룬다. ## 정리 모델은 텍스트를 출력하고, 하네스가 그 가운데 도구 호출을 골라 실행한 뒤 결과를 다시 텍스트로 돌려준다. 에이전트가 파일을 고치고 테스트를 실행하는 것은 이 과정이 되풀이된 결과다. 실행이 하네스를 거치므로 에이전트가 한 일은 기록으로 남고, 같은 자리에서 권한 규칙, 승인, 샌드박스로 실행을 통제할 수 있다. 모델에 무엇을 어떤 형태로 보여 주고 돌려주느냐가 결과를 바꾸므로, 에이전트의 성능과 안전은 모델과 하네스가 함께 정한다. 이 루프가 코드 작업에서 돌아가려면 조건이 하나 더 필요하다. 도구 결과가 다음 판단의 근거가 되려면 결과가 빨리, 분명하게 돌아와야 한다. 코드에서는 실행과 테스트가 그 역할을 한다. 8.4절은 이 특성을 다룬다. ## 참고문헌 학술 자료는 게재처의 종류를, 그 밖의 자료는 자료의 성격을 함께 적었다. 1.
